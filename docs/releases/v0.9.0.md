# v0.9.0 beta

This beta assembles Momus's supported review capabilities and the evidence
tooling needed to evaluate them. It follows v0.3.1 through PRs
[#40](https://github.com/brianluby/momus-review/pull/40),
[#41](https://github.com/brianluby/momus-review/pull/41),
[#42](https://github.com/brianluby/momus-review/pull/42), and
[#43](https://github.com/brianluby/momus-review/pull/43).

## Changes since v0.3.1

- **Repository evidence checks:** opt-in `momus review --docs-drift` compares
  supported source-linked Rust Markdown examples with public interfaces.
  `--upgrade-triage` compares Cargo/npm manifests and lockfiles with exact
  dependency/version-matched local release notes. Both produce advisory
  findings with source locations and explicit unknowns. See [docs drift](../docs-drift.md)
  and [dependency triage](../upgrades.md).
- **Local onboarding tours:** `momus tour` produces bounded, redacted stops,
  components and uniquely resolved static Rust/JS/TS import maps without API
  calls. Inferred roles are hypotheses; Python, dynamic and external import
  relationships remain unknown. Tours read the working tree and can write
  index-cache metadata. See [tours](../tours.md).
- **Separate merge outcomes and prospective collection:** revert, incident and
  flake evidence have distinct observation windows and chronological evaluation.
  Insufficient history produces null estimates. The offline collector freezes
  premerge reports, joins exact merged heads and exports independently supplied
  observations with an availability audit. External receipt authenticity and
  surveillance remain the operator's responsibility. See [merge outcomes](../merge-confidence.md)
  and [collection protocol](../outcome-collection.md).
- **Momus-owned product evaluation:** a 36-case suite includes 13 authored core
  defect/fixed pairs, two docs/dependency pairs, four insufficient-evidence cases
  and two exposed development controls. Source-reviewed annotations, offline
  behavioral probes, isolated materialization and issue-level adjudication keep
  labels separate from review inputs. Missing or incomplete cases retain their
  full denominators and earn no detection credit. See [product benchmarks](../../eval/momus/README.md).
- **Acceptance hardening:** native absolute review scopes bind to version-2
  materialization receipts; wrong roots/subdirectories, dropped context,
  incomplete source coverage and malformed evidence cannot earn issue credit.
  Native CLI-to-scorer docs controls were checked on macOS without model calls;
  Windows path handling has offline regressions, without Windows end-to-end evidence.
- **Rust API contracts:** substantive caller invariants and failure/unknown
  boundaries, 14 new executable offline examples (15 total), and dedicated
  rustdoc CI cover representative evidence, location, redaction, cache, budget
  and approval contracts. See [Rust API documentation](../rust-api-contracts.md).

## Beta use and limits

Start with a scoped review and inspect the report and affected source manually:

```sh
momus review --base origin/main --upgrade-triage --docs-drift
momus tour . --exclude 'vendor/**' --markdown
momus confidence --report reviews/latest.json
```

Ordinary review/scan sends code and context to the configured System One
endpoint, the external TypeSafe Jev API by default. Redaction is best effort;
raw local reports can retain original source and credentials. Treat reports,
caches and published artifacts according to the repository's data policy.
The local docs/dependency analyses make no API calls themselves, but adding
their flags does not disable the review's model calls.

Docs checks cover structural argument counts and evidenced interface removals
within the supported Rust syntax, not example execution or semantic correctness.
Dependency advisories do not verify downstream callers or all intervening
releases. Discovery of a source language does not establish equal review
coverage or accuracy across languages. Review findings and proposed tests need
human validation; generated scaffolds supply no coverage until completed.

Automatic approval remains disabled by default and requires separate trusted
policy/history plus fresh complete current-head evidence when explicitly enabled.
Missing evidence stays unknown. Neither this beta nor its offline fixtures
establishes model accuracy, real-history calibration or production outcome rates;
the product-results template remains blank.
