# Dependency upgrade and changelog triage

Run `momus review --upgrade-triage` with the normal review options to include local dependency triage. The JSON report's optional `upgrades` contains `changes` and explicit `unknowns`. Its advisory findings join the report's top-level `findings` and normal suppression flow. Each change identifies its ecosystem, dependency, manifest/lockfile scope, old and new version, change kind, risk signal, and evidence locations. Evidence distinguishes the base snapshot from the current snapshot; removals cite the base declaration.

The analysis reads the bounded repository evidence supplied to review. It does not fetch upstream release notes, install dependencies, or run package managers. Supply relevant dependency release notes in the repository when available; missing release notes remain unknown. Excluded or unavailable evidence cannot establish compatibility.

Supported inputs are Cargo manifests and lockfiles, npm `package.json`, and npm v1-v3 `package-lock.json` or `npm-shrinkwrap.json`. Cargo workspace declarations, development/build dependencies, target-specific dependencies, renamed packages, npm dependency groups, aliases, and nested lockfile resolutions retain their own scopes. Lockfiles can reveal resolved upgrades even when a manifest requirement did not change. Concurrent Cargo versions are matched only when unchanged versions leave a unique old/new pair; ambiguous pairs remain explicit additions/removals with an uncertainty notice. Cargo workspace/path packages without an external lockfile source are not treated as third-party resolved upgrades.

Major version changes, incompatible pre-1.0 changes, downgrades, removals, and matched release-note breaking signals produce compatibility review advisories. An ordinary semver upgrade produces a `semverCompatibleSignal`, which is a heuristic signal rather than a claim that all callers remain compatible. A removal requires checking for remaining consumers. An addition identifies the new dependency without inventing a defect.

Release-note evidence requires both the dependency identity and an exact target version. The dependency can be identified by its directory, a dependency-prefixed changelog filename, or the release heading. A repository-wide changelog for a different project, an unmatched version, or an arbitrary file containing the word “breaking” cannot support a finding. The bounded target release excerpt includes source references and retains an uncertainty notice: intervening releases and downstream usages are not verified. A caret/tilde manifest requirement alone does not identify the resolved target release; the lockfile can supply an exact version.

Changed Cargo dependency features/options, Cargo patch/replace/feature resolution, and npm overrides/resolutions/workspace/peer metadata are recorded as unknown where complete resolution is unavailable. npm lockfile schema migrations preserve resolved package identity across v1-v3; unsupported lockfile versions remain unknown. Unsupported ecosystem manifests/locks, malformed input, unresolved workspace versions, source-based versions, ambiguous ranges, prereleases, missing matched changelogs, and exceeded dependency limits remain explicit unknowns. Their absence never becomes evidence of low risk. Unsupported requirements are displayed with a neutral placeholder; all evidence follows the review's secret-redaction rules.

Before accepting an upgrade, check affected callers, review all intervening upstream release notes, apply migrations, and run the affected packages' build and API/behavior regression tests. The triage's finding probabilities describe the observed compatibility signal, not the probability of breakage. No calibration or real-world incident-rate claim is made. Findings use the normal report schema, fingerprints, suppression, and advisory comment action; release notes alone do not request changes.
